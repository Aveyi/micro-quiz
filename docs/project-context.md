## 1. Коротко

Учебный проект: **онлайн-викторина в стиле Kahoot**. Ведущий создаёт викторину и запускает игру, игроки подключаются по коду комнаты и отвечают на вопросы на время, таблица лидеров обновляется в реальном времени.

Система состоит из двух микросервисов, общей PostgreSQL, балансировщика nginx и десктопного приложения:

| Часть | Технологии | Владелец |
|---|---|---|
| `content`: аккаунты ведущих, викторины, вопросы | Python, FastAPI, REST | участник 2 |
| `live`: комнаты, проведение игры, очки, история игр | Go, WebSocket (+ REST) | участник 1 |
| Десктопное приложение | Python, PySide6 | оба, по экранам |
| docker-compose, nginx, миграции, CI | Docker, nginx, golang-migrate | участник 1 |

### Обратная связь преподавателя

Первая тема, «трекер игрового турнира», была отклонена: преподаватель сказал, что микросервисы в ней «притянуты» и всё можно сделать монолитом. В пример он привёл упрощённый аналог Discord, где разделение оправдано.

Поэтому тему сменили. Обоснование микросервисов в новой теме **обязательно** проговаривать на защите и в отчёте:
- **Разная нагрузка.** `content` получает редкие короткие запросы, а `live` во время игр держит много постоянных соединений и пиковую нагрузку в момент вопроса.
- **Независимое масштабирование.** Несколько инстансов `live` за nginx, `content` может работать в одном.
- **Изоляция отказов.** Если упал `live`, аккаунты и викторины целы.
- **Язык под задачу.** Python для CRUD, Go для тысяч соединений.
- **Изоляция данных.** У каждого сервиса своя схема и свой пользователь БД (database per service).

## 3. Команда и окружение

| | Участник 1 | Участник 2 |
|---|---|---|
| Сервис | `live` (Go) | `content` (Python, FastAPI) |
| ОС | macOS, Apple M3 Pro (**arm64**) | Windows (**x86-64**) |
| Интересы | DevOps; изучает Go (до проекта знал только синтаксис) | Python |

Что из этого следует:
- **`.exe` собирает участник 2.** PyInstaller не собирает под чужую ОС. Как альтернатива — GitHub Actions с Windows-раннером.
- **Docker-образы каждый собирает у себя.** Официальные образы мультиархитектурные. Если понадобится обмениваться готовыми образами, нужен `docker buildx --platform linux/amd64,linux/arm64`.
- **Концы строк.** Во всём репозитории `LF` (`.gitattributes`), иначе shell-скрипты в Linux-контейнерах ломаются из-за `CRLF` с Windows.

## 4. Ключевые решения и причины

Подробности — в [`quiz-design.md`](quiz-design.md).

| Решение | Почему |
|---|---|
| Игроки входят по коду комнаты и нику, без регистрации | как в Kahoot; аккаунт нужен только ведущему |
| Один правильный вариант, таймер у каждого вопроса, бонус за скорость (500–1000 очков) | простые и понятные правила |
| В идущую игру войти нельзя; обрыв связи — игрок выбывает; ушёл ведущий — игра отменяется | меньше сложных состояний |
| Время ответа измеряет сервер | часам клиентов доверять нельзя |
| Сообщения WebSocket: `{"type": ..., "data": {...}}` | единый формат, протокол легко расширять |
| Токен ведущего — в заголовке `Authorization`, код комнаты — в `?room=` | токен не попадает в логи; по коду комнаты nginx выбирает инстанс |
| nginx для `/live/ws`: `hash $arg_room consistent` | комната живёт в памяти одного инстанса, и все её участники должны попасть на него |
| `live` берёт вопросы у `content` по REST через `/internal` (с `X-Internal-Token`, наружу не открыт) | граница между сервисами; правильные ответы не доступны игрокам |
| JWT HS256 от `content`, `live` проверяет сам по общему `JWT_SECRET` | `live` не нужно ходить в `content` на каждое подключение |
| Одна PostgreSQL, схемы `content` и `live`, у каждого сервиса свой пользователь БД | централизованная БД по ТЗ + изоляция данных сервисов |
| Ответы игроков пишутся в БД пакетом в конце вопроса | меньше нагрузки на БД в пиковый момент |
| Миграции через golang-migrate, каждый пишет только для своей схемы | один способ создавать таблицы на всех |
| Десктоп на PySide6 | язык участника 2, зрелый фреймворк, есть WebSocket-клиент |
| Монорепозиторий | общие контракты и `docker-compose` в одном месте |

## 5. История и что переиспользуется

До смены темы участник 1 сделал сервис **live-табло турнира** (папка `scoreboard/`). Он прошёл работы 1 и 2 по старой теме:
- WebSocket-хаб на `gorilla/websocket`: одна горутина хаба, на каждого клиента `readPump` + `writePump` (единственный читатель и единственный писатель соединения), ping/pong, отключение медленных клиентов;
- graceful shutdown: `signal.NotifyContext`, сначала `http.Server.Shutdown`, затем закрытие WebSocket-клиентов кодом 1001 и ожидание их отключения;
- хранилище матчей в памяти с `RWMutex`, REST-ручки, встроенная через `embed` веб-страница;
- multi-stage Dockerfile (alpine, 24 МБ, пользователь с UID 10001, `HEALTHCHECK` через `wget` на `$PORT`, exec form) и `.dockerignore` по белому списку. **Dockerfile написал сам участник 1**, проверен и протестирован.

| Переиспользуется в `live` | Уходит |
|---|---|
| хаб и клиенты (хаб → «комната») | модель матча и хранилище в памяти |
| graceful shutdown, настройки `http.Server` | веб-страница табло (интерфейс переезжает в десктоп) |
| подход к Dockerfile и `.dockerignore` | `PATCH /matches/{id}` |
| соглашения: конверт сообщений, ошибки `{"error": ...}`, `snake_case` | |

`docs/scoreboard-guide.md` — разбор кода табло и теория для защиты (WebSocket, горутины, каналы, гонки, `context`, graceful shutdown, безопасность). Почти вся теория остаётся актуальной и для `live`.

## 9. Правила для агентов, работающих с проектом

- Контракты (сообщения WebSocket, REST, схема БД, переменные окружения) — только по [`quiz-design.md`](quiz-design.md). Меняется контракт — сначала правится документ, и об этом сообщается второму участнику.
- Сервис работает **только со своей схемой БД**. Данные другого сервиса берутся через его API.
- `/internal` API не проксируется через nginx и требует `X-Internal-Token`.
- Секреты не коммитятся: `deploy/.env` в `.gitignore`, в репозитории только `deploy/.env.example`.
- Учитывать кроссплатформенность: Windows и macOS, arm64 и amd64, концы строк `LF`.
- Участник 1 учится и хочет разбираться в каждом шаге: объяснять решения, а не просто выдавать код. Dockerfile он написал сам (агент только проверял и подсказывал); по остальным DevOps-частям (compose, nginx) перед тем, как писать за него, уточнить, хочет ли он сделать это сам.
